# 通知与账户配置教程

在工作台登录后，打开“通知配置”。每个渠道可以独立启停，密钥输入框留空表示保留服务器原值。保存操作验证格式和配置完整性，不会自动发送测试消息。

## Bitget 账户连接

本项目只读取账户、持仓、成交和历史数据。

1. 登录 Bitget，在 API 管理中创建供此监控使用的 API Key。
2. 记录 **API Key、Secret、Passphrase** 三项。Passphrase 是创建 API 时设置的口令，不是网页管理密码。
3. 只启用读取监控所需的权限，不启用交易、划转或提现权限。可将允许访问的 IP 限定为部署服务器的实际出口 IP。
4. 将三项凭据写入服务器 `config/.env` 的 `BITGET_API_KEY`、`BITGET_API_SECRET`、`BITGET_API_PASSPHRASE`。
5. 按账户实际类型设置 `BITGET_ACCOUNT_MODE=classic` 或 `uta`。经典合约账户可通过 `BITGET_PRODUCT_TYPES` 选择支持的产品类型；初始示例为 `USDT-FUTURES`。
6. 启动监控，确认日志中同步正常，并核对网页的账户币种、持仓方向和数量。

账户凭据由服务器配置提供，网页只开放通知设置。更换账户前先备份；不同账户应使用独立数据，避免历史混用。

资料：[Bitget 官方 API 文档](https://www.bitget.com/docs/intro)、[统一账户 API](https://www.bitget.com/docs/uta/rest-api)。

## Telegram：Token 与 Chat ID

### 创建机器人

1. 在 Telegram 找到官方 **@BotFather**。
2. 发送 `/newbot`，按提示填写机器人名称与用户名。
3. 保存 BotFather 返回的 Bot Token。Token 控制机器人发送消息，不能公开。

### 准备接收目标

- **私聊**：打开新机器人并点击“开始”，或发送一条消息。
- **群聊**：把机器人加入目标群，确认具有发送消息的权限。
- **频道**：将机器人添加到频道，并授予发布消息所需的权限。

### 获取 Chat ID

对于**尚未接入其他程序、没有 webhook 的新机器人**，先向它发送一条消息，再在你自己的可信 HTTP 客户端调用：

```text
GET https://api.telegram.org/bot<BOT_TOKEN>/getUpdates
```

在返回的更新中读取 `message.chat.id`；频道消息可能出现在 `channel_post.chat.id`。群或频道的数字 ID 可能带负号，必须完整保留。不要把包含 Token 的请求地址、响应或截图发到公开 Issue。

已经运行中的机器人不要另开长轮询，也不要为获取 ID 删除其 webhook，这会干扰既有消息处理。可使用原配置中确认过的 Chat ID；已知公开超级群或频道也可按官方 `getChat` 接口查询目标。

### 填入工作台

填写 Token 和 Chat ID，启用 Telegram，再选择：

| 配置 | 行为 |
| --- | --- |
| 持仓卡片 | 展示开仓及持仓参数，后续更新原消息 |
| 加仓 / 减仓 / 平仓 | 额外发送对应交易事件 |
| 卡片刷新间隔 | 控制卡片目标更新频率，不延迟独立事件队列 |

保存后等待配置生效。私人用户的用户名不能替代数字 Chat ID。若更换机器人或接收目标，程序会建立新的消息引用，避免继续编辑旧目标中的卡片。

收不到消息时，检查是否已点击“开始”、机器人是否被移出或禁言、Chat ID 是否正确。平台限流会触发等待与退避，设置很短的刷新间隔不保证每次都能立即完成编辑。

资料：[Telegram 机器人教程](https://core.telegram.org/bots/tutorial)、[Bot API：getUpdates / getChat](https://core.telegram.org/bots/api)。

## Discord：Webhook

1. 在目标 Discord 服务器打开“服务器设置 → 集成”。操作账号需要管理 Webhook 的权限。
2. 创建 Webhook，为它命名并选择接收消息的文字频道。
3. 复制完整 Webhook URL。常见结构为：

```text
https://discord.com/api/webhooks/<WEBHOOK_ID>/<WEBHOOK_TOKEN>
```

4. 在工作台启用 Discord，填入完整地址，选择持仓卡片及需要的加减仓、平仓事件。
5. 设置整数秒的卡片刷新间隔，保存并等待生效。

不要添加 `/github` 等其他服务专用后缀。完整 Webhook 地址包含发送凭据，须保密。持仓卡片更新原消息，不会按刷新频率不断创建新消息。

如果 Webhook 被删除，请重新创建并保存新地址。如果仅在 Discord 中恢复了原 Webhook 的权限、地址没有变化，请在工作台**关闭 Discord 并保存，等待生效，再开启并保存**，让通知重新连接。没有修改的保存不会触发监控重启；管理员也可以重启监控服务。

资料：[Discord 官方 Webhook 介绍](https://support.discord.com/hc/en-us/articles/228383668-Intro-to-Webhooks)。

## Bark：服务器与设备 Key

Bark 用于手机上的开仓方向成交提醒，包含加仓成交；不提供持仓看板或平仓通知。

1. 在手机 Bark 中允许系统通知。
2. 使用自建 Bark 时，先在 App 内添加并选择对应服务器，完成设备注册。
3. 找到个人推送地址，将服务器与设备 Key 分开：

```text
个人推送地址：https://push.example.com/DEVICE_KEY/示例内容
服务器地址：https://push.example.com
设备 Key：DEVICE_KEY
```

4. 在工作台填写服务器根地址和设备 Key，不要把后面的测试内容一起粘贴。
5. 选择声音、通知分组、持续响铃开关和成交核对间隔，启用后保存。

外部服务器使用 HTTPS。与本项目同机部署的 Bark 可以使用 `http://127.0.0.1:8080`；这个地址指的是**运行监控的服务器**，不是你的手机。设备 Key 必须是在相应 Bark 服务器上注册获得的，不同服务器的 Key 不能混用。

自定义声音需要先在 Bark 中导入，配置的名称应与导入名称一致。没有声音或推送时，检查 iOS 通知权限、专注模式、App 当前服务器及设备 Key。启用“持续响铃”不代表可以绕过手机系统设置。

资料：[Bark 官方教程](https://bark.day.app/#/tutorial)、[Bark 项目](https://github.com/Finb/Bark)。

## 保存与状态如何理解

| 页面状态 | 含义 |
| --- | --- |
| 已保存 | 配置已写入服务器 |
| 配置生效中 | 新配置等待监控重新加载 |
| 配置已生效 | 监控已加载该版本，并完成一次持仓同步 |
| 同步正常 / 监控心跳 | 主监控循环近期完成同步 |
| 最近接口确认 | 通知服务接受了请求，不等于手机送达或用户已读 |
| 待处理 / 历史失败 | 本地事件处理记录，不能独立代表所有渠道的实时可用性 |

有实际变更的保存会更新版本，由 systemd 重启监控加载。短暂重连是正常过程。没有改动的保存不会增加版本，也不会重启。

如果另一个页面先保存了新配置，当前页面会提示冲突。点击“重新读取”，确认最新值后再修改，避免覆盖其他页面的修改。保存与应用期间表单暂时锁定。

密钥只写入、不回显；关闭渠道会保留凭据。恢复渠道时不会批量补发停用期间的历史事件。改变 Telegram / Discord 接收目标时，原消息引用会隔离，避免误编辑旧目标。

## 常见问题

### 保存成功，为什么还不能确定通知能收到？

保存检查格式与必填项，并不向真实渠道发送测试通知。监控心跳也不等于每个渠道的凭据都有效。应结合后续真实事件、渠道消息与服务器日志核对。不要在公开 Issue 中粘贴 Token、Webhook、设备 Key 或完整私密日志。

### 为什么会出现重复提醒？

平台可能已经接受请求，但监控因网络超时没拿到回执。普通事件和 Bark 会重试，这种边界下可能重复；直接丢弃不确定结果则可能漏通知。项目不承诺严格的“只投递一次”。

### 为什么历史或收益稍后才补全？

交易所历史、手续费或结算数据可能晚于持仓变化可用。待结算记录会保留重试，其他新交易事件继续处理。历史范围取决于接口实际返回，页面统计不能替代交易所对账单。

### 为什么直接打开 IP 的数据接口被拒绝？

整个工作台采用可信 HTTPS 代理和登录会话。请使用配置的 `BITGET_WEB_ORIGIN` 加上 `/bitget/`，并核对 Nginx 的域名、转发协议和实际代理来源。不要把网页监听端口直接当作公开访问入口。

### 手动改了 .env，为什么网页中的通知值没变？

一旦通过网页保存了通知设置，`data/web-notification-settings.json` 中对应字段优先。日常通知修改应通过网页完成；交易所凭据和部署参数仍由 `config/.env` 提供。
